# /testpilot — 1С через клиент тестирования

MCP-сервер [1c-testpilot](https://github.com/ROCTUP/1c-testpilot) подключается к клиенту
тестирования 1С и даёт 10 инструментов `tc_*` (действие выбирается параметром `action`).
С версии 1.7.0 рядом пять инструментов внешней обработки Testpilot — код, запросы и
метаданные прямо в сеансе 1С, раздел «Обработка» ниже:

| Инструмент | О чём |
|---|---|
| `tc_session` | запуск и остановка клиента, подключения, журнал вызовов |
| `tc_app` | активное окно, дерево объектов, ошибки, снимок экрана |
| `tc_window` | навигация `e1cib/...`, командный интерфейс, ответы на вопросы, сообщения |
| `tc_find` | поиск объектов в дереве UI, ожидание появления |
| `tc_form` | управляемая форма: обзор, снимки состояния, фокус |
| `tc_field` | поля и кнопки: чтение, ввод, клик, списки выбора |
| `tc_table` | строки таблиц и деревьев: чтение, поиск, добавление, правка |
| `tc_doc` | табличный документ: чтение области, поиск текста, сохранение |
| `tc_calendar` | поле календаря |
| `tc_scenario` | запись и воспроизведение сценария (uilog) |

Каждый инструмент сам печатает список действий с параметрами — спроси его схему,
прежде чем гадать.

Полная актуальная матрица действий и параметров хранится в [references/tools.md](references/tools.md).
Для повторяемых прогонов доступны [именованные профили](references/profiles.example.yaml),
необязательный [Python/pytest API](references/python-testing.md) и
[дайджест обработки Testpilot](references/epf.md). Эти reference-файлы синхронизированы
с текущим `1c-testpilot`; список действий в них важнее сокращённой таблицы выше.

## Обработка Testpilot: код, запросы и метаданные в сеансе 1С

Внешняя обработка `Testpilot.epf` открывается сервером вместе с клиентом (`launch_client`
сам подаёт её через `/Execute` и подтверждает штатное предупреждение безопасности).
Через неё работают пять инструментов без параметра `action`:

| Инструмент | Параметры | Результат |
|---|---|---|
| `tc_execute_code` | `code*`, `context*` (`client`/`server`), `parameters={}`, `timeout=180` | `result` |
| `tc_execute_query` | `query*`, `parameters={}`, `limit=100` (1–500), `timeout=180` | `columns`, `rows`, `returned_rows`, `truncated` |
| `tc_get_metadata` | `name` либо `meta_type` + `search`/`field_search`; `sections`, `limit`, `offset` | обзор, список или структура объекта |
| `tc_list_custom_bsl_functions` | — | `functions`: зарегистрированные BSL-функции |
| `tc_execute_custom_bsl_function` | `name*`, `parameters={}`, `timeout=180` | `result` |

Включаются в `.env` сервера, по умолчанию всё выключено; смена настроек требует
перезапуска сервера. В нашем стенде включены код и запросы:
`TC1C_CODE_EXECUTION=true`, `TC1C_QUERY_EXECUTION=true`, `TC1C_METADATA=auto`,
`TC1C_CODE_EPF=D:/Project/MCP/1c-testpilot/onec/Testpilot/Testpilot.epf` (EPF в uv-пакет
не входит — лежит рядом с `.env`, при обновлении скачивается с гита). В профиле запуска
можно переопределить путь параметром `code_epf`. Полные примеры — [references/epf.md](references/epf.md).

Примеры вызовов:

```json
// код: параметры доступны как соответствие «Параметры», результат присваивается «Результат»
{"context": "server", "code": "Результат = Параметры[\"текст\"] + \"!\";",
 "parameters": {"текст": "Проверка"}}

// запрос: текст и значения передаются раздельно; пакет с ПОМЕСТИТЬ/УНИЧТОЖИТЬ — одним query
{"query": "ВЫБРАТЬ Код, Наименование ИЗ Справочник.Номенклатура ГДЕ Наименование ПОДОБНО &Имя",
 "parameters": {"Имя": "%чай%"}, "limit": 100}

// метаданные: обзор конфигурации → поиск объектов → подробности по точному имени
{}
{"meta_type": "Документ", "search": "заказ", "limit": 20}
{"name": "Документ.ЗаказКлиента", "sections": ["fields", "table_parts"]}
```

Даты, ссылки и перечисления ходят в типизированном JSON
(`{"$type": "ref", "metadata": "Справочник.Номенклатура", "uuid": "…"}`), полученную
ссылку можно целиком вернуть в `parameters` следующего вызова. К запросу `РАЗРЕШЕННЫЕ`
добавляется автоматически; запросы и код выполняются с правами пользователя и учитывают
RLS — пустая выборка не доказывает отсутствие данных.

Грабли:

- `unknown_metadata_type` и `invalid_metadata_sections` — API метаданных
  строгий: `meta_type` называется русскими именами из обзора конфигурации
  («Обработка», не «DataProcessor»), а `sections` — только `fields`,
  `table_parts`, `values`, `properties` («attributes», «dimensions»
  отклоняются).
- `helper_not_ready` — клиент подключён без обработки (например, чужой уже открытый).
  Перезапусти клиент через `launch_client` — сервер сам откроет EPF.
- Истёкший `timeout` **не отменяет** код: следующий вызов вернёт
  `previous_execution_completed` с `previous_result`, а новый код в нём не запускается.
- `connection_busy` — соединение занято другим вызовом: смотри `list_connections`
  (`busy`, `active_action`, `active_seconds`); ожидание очереди ограничено
  `TC1C_QUEUE_TIMEOUT=60`.
- По умолчанию запрещены идентификаторы `Записать`, `Удалить`, `УдалитьФайлы`,
  `УстановитьПривилегированныйРежим`, `COMОбъект`, `СоздатьКаталог` и др.;
  `Выполнить`/`Вычислить` запрещены всегда. Фильтр — не песочница: процедура
  конфигурации может менять данные без запрещённых слов в переданном тексте.

## Порядок работы

### 1. Убедиться, что сервер поднят

`tc_*` не отвечают → сервер не запущен. Поднять:

```bash
1c-testpilot --env-file D:/Project/MCP/1c-testpilot/.env   # streamable-http, 0.0.0.0:6014
```

Без `--env-file` файл `.env` не читается. За MetaMCP сервер заведён как
`http://host.docker.internal:6014/mcp`.

Порт `6014` — порт нашего локального стенда. В других установках проверь фактические
`TC1C_HTTP_PORT`, `TC1C_HTTP_HOST`, `TC1C_HTTP_PATH` и `TC1C_TRANSPORT` в окружении процесса,
а не подставляй порт из примера вслепую.

Для диагностики и повторяемости также фиксируй нужные переключатели сервера:
`TC1C_PROFILES_FILE` (профили), `TC1C_RESPONSE_FORMAT=toon|json`,
`TC1C_COMPACT_REFS=id|prefix|off`, `TC1C_READBACK=true|false`,
`TC1C_VERIFY_TARGET=true|false`, `TC1C_SNAPSHOT_LIMIT` и `TC1C_LOGGING`.
Значения задаются процессу TestPilot до его запуска; `.env` MCP-клиента сам по себе их не
подхватывает. После правки `.env` сервер перезапускают — файл читается только на старте
(автозапуск: `start-hidden.vbs`; руками: та же команда из пункта выше).

### 2. Клиент: запустить свой или подключиться к чужому

```
tc_session(action="list_connections")          # кто уже подключён
tc_session(action="launch_client", base="C:/Base/Demo", user="…", password="…",
           version="8.3.27.1936", wait=300)    # файловая база
tc_session(action="launch_client", base="Сервер\\База", server=true, user="…", password="…")
tc_session(action="connect", port=<порт>)      # к уже запущенному /TESTCLIENT -TPort
tc_session(action="list_profiles")             # доступные именованные профили
tc_session(action="launch_client", profile="<имя>")
```

- **Логин обязателен параметрами.** Если база спрашивает пользователя, клиент встанет на
  окне «Доступ к информационной базе», которое протоколу тест-клиента не видно:
  `get_active_window` вернёт `ok: false, addressable: false`, поиск объектов — ошибку
  «Could not read application windows». При этом `launch_client` рапортует `ok: true`.
  Диагноз ставится `tc_app(action="get_screenshot")`.
- Несколько клиентов — во всех вызовах без `ref` нужен `connection_id`.
- Подключения живут в процессе сервера, а не в сессии MCP: брошенный `launch_client`
  оставляет висеть клиент 1С. **Закрывай за собой:** `tc_session(action="stop_client",
  connection_id=…)`, потом `list_connections` для проверки.
- `desktop="isolated"` уводит окна клиента с рабочего стола пользователя.
- Для уже запущенного чужого/владельческого клиента используй `disconnect`, а не
  `stop_client`; остановка допустима только для своего тестового клиента.

### 3. Пройти стартовые окна

Демо- и рабочие базы встречают мастерами: «Подключение интернет-поддержки», «Информация»,
«Путеводитель», «Рекомендуется обновить версию конфигурации», «Установка соединения
с 1С:Документооборот». Это обычные формы: `tc_window(action="close_window")` либо клик
по «Отмена» из `tc_find(action="find_objects", cls="Button")`. После каждого закрытия
читай `get_active_window` — окна идут пачкой.

### 4. Навигация

Надёжнее кликов по разделам — навигационная ссылка:

```
tc_window(action="execute_command", command="e1cib/list/Справочник.Контрагенты")
tc_window(action="execute_command", command="e1cib/app/Отчет.ОборотноСальдоваяВедомость")
```

**Панель разделов и главное меню протоколу не видны:** у `MainFrame` нет детей,
`get_command_interface` на начальной странице отвечает `unsupported_receiver`, а на форме
возвращает пустой `CI`. Значит, разделы, «Все функции» и «Файл → Открыть» кликом не
достать — ходи навигационными ссылками и по тому, что лежит на адресуемых формах.
Внешнюю обработку так не открыть: нужно знать имя объекта или брать её из списка
`e1cib/list/Справочник.ДополнительныеОтчетыИОбработки`. Исключение — сама обработка
Testpilot: при включённых инструментах выполнения сервер открывает её при `launch_client`
без всякой навигации.

Неверная ссылка возвращает `code: navigation_failed` и окно `ErrorWindow` — не падение.
Имя объекта бери из метаданных, не выдумывай (`Отчет.РасчетныйЛисток` в ЗУП 3.1 нет).
Формы рисуются не мгновенно: после открытия —
`tc_find(action="wait_for_object_displayed", cls="Table", timeout=60)`.

### 5. Чтение

```
tc_form(action="get_context", include_tables=true, max_rows=50)   # обзор формы целиком
tc_find(action="find_objects", cls="EditField")                   # только элементы
tc_field(action="read_fields", targets=[{"ref": "…"}, {"ref": "…"}])
tc_table(action="read_rows", ref=<таблица>, max_rows=50)
tc_table(action="find_rows", ref=<таблица>,
         conditions=[{"column": "Наименование", "text": "Ромашка"}])
tc_doc(action="read_document", ref=<поле табличного документа>, max_cells=1000)
tc_doc(action="find_text", ref=<поле>, text="Итого")
```

Для регрессионного сравнения формы можно сохранить состояние и сравнить его после действия:

```
tc_form(action="create_snapshot", include_tables=true, max_rows=500)
tc_form(action="compare_snapshot", snapshot_id="<id>")
```

Снимки живут в памяти сервера до удаления, вытеснения или его остановки; для долгого
прогона сохраняй внешний артефакт, а не полагайся только на `snapshot_id`.

- `get_context` на типовой форме — это 150+ элементов; когда нужен один реквизит, дешевле
  `find_objects` по имени и `read_fields`.
- `find_rows` ищет **подстроку** (`*` и `?` не работают, в отличие от `find_objects`) и
  только на **активной** форме; чужая форма → `code: target_not_interactive`.
  При неверной колонке сервер возвращает `available_columns` — читай их.
- Пустой ответ таблицы ≠ пустая база: список мог не догрузиться или иметь отбор.
- Отчёт на большой базе строится дольше, чем возвращается клик «Сформировать»: первый
  `read_document` может вернуть `rows: 0` — прочитай ещё раз.

### 6. Запись

```
tc_field(action="set_fields", entries=[{"ref": "…", "text": "Ромашка"},
                                       {"ref": "…", "checked": true}])
tc_table(action="add_rows", ref=<таблица>, rows=[{"cells": [{"column": "<имя элемента>",
                                                             "text": "100"}]}])
tc_table(action="set_row_values", ref=<таблица>, cells=[…])   # текущая строка
```

- Колонка адресуется **именем элемента** (`ХозрасчетныйСчетДт`), не заголовком; имена —
  `tc_find(action="find_objects", root_ref=<ref таблицы>)`.
- **Ссылочные поля текстом не заполняются.** Ввод кода оставляет открытым автоподбор
  («нет в списке. Нажмите Показать все»), и заполнение строки встаёт с
  `code: column_not_current`, `drop_list_open: true`; `choose_from_drop_list` на такой
  колонке отвечает `unsupported_receiver`, а `close_drop_list` и `activate` соседа список
  не гасят — строку придётся отменить `tc_table(action="end_edit_row", cancel=true)`.
  Рабочий порядок:

  ```
  tc_field(action="activate", ref=<поле>)
  tc_field(action="open_drop_list", ref=<поле>)
  tc_field(action="get_choice_list", ref=<поле>)      # что предлагает платформа
  tc_field(action="choose_from_drop_list", ref=<поле>, value="Конфетпром ООО")
  ```

  Либо `tc_field(action="start_choosing")` → форма выбора → `tc_table(action="goto_row")`
  и `choose_row`.
- Галочки в строках таблицы: массовая расстановка — цикл `goto_row` → `activate`
  → `set_check` (64 пары подряд в прогоне 1114 без единого отказа, ~0,2 с на
  строку). Состояние галочки читается `read_rows` той же таблицы: `current_check`
  не поддержан, а чекбокс ячейки отдельным объектом `find_objects` не находит.
- Сначала шапка (организация, дата), потом табличная часть: пустая организация сужает
  подбор в строках.
- `set_fields` сам сверяет записанное: смотри `verified` и `verification: exact`.
- `ok: true` означает «команда принята», а не «данные записались». Проверяй результат
  чтением: строка появилась в списке, документ проведён, поле содержит нужное.
- После `Записать`, `Провести` или операции, которая должна создать движение, резерв
  или связанный объект, обязателен read-back из документа/списка и целевого регистра.
  Наличие строки или суммы само по себе не доказывает проведение: сверяй статус,
  UUID, движения и остаток/резерв. При расхождении фиксируй фактический отказ или
  `BLOCKED`, не объявляй подготовленный объект успешным результатом.

### 7. Диалоги и сообщения

```
tc_window(action="answer_dialog", confirm=false, timeout=8)   # «Сохранить изменения?» → Нет
tc_window(action="close_user_messages_panel")                 # перед действием
tc_window(action="get_user_message_texts")                    # после действия
```

`click(diagnostics=true)` часто отвечает `user_messages_unavailable` — панель сообщений
закрыта; это не признак ошибки. Чтобы сообщения относились к одному действию, гаси панель
до него.

### 8. Когда не видно, что происходит

`tc_app(action="get_screenshot", scale=60)` снимает окно вместе со всплывающими списками —
единственный способ увидеть платформенные окна (логин, автоподбор). Работает, когда сервер
и клиент на одном компьютере.

Сложный разбор: `tc_session(action="start_logging")` → действия →
`get_logging_status` → `stop_logging` вернёт JSONL и HTML-отчёт со снимками.
Журнал остаётся в `logs/session-*` сервера: `events.jsonl`, `report.html`,
`screenshots/`, маркер `completed` — сессия закрыта.

Альтернативный путь для автоматизированной регрессии — Python API и pytest. Он обращается
к клиенту тестирования напрямую и не требует MCP-сервера; минимальный запуск и fixture-паттерны
см. в [references/python-testing.md](references/python-testing.md).

## Безопасность

- Клиент тестирования **вводит данные по-настоящему**. На рабочей базе: только чтение —
  открыть форму, прочитать поля, прочитать таблицу или отчёт. Никаких кликов «Провести»,
  «Записать», «Пометить на удаление» без явного разрешения владельца базы.
- Пробовать сценарии — на демо- или тестовой копии.
- Инструменты обработки выполняют **произвольный BSL с правами пользователя 1С**.
  На рабочей базе — только код и запросы на чтение; если нужен лишь запрос,
  включай один `TC1C_QUERY_EXECUTION` без `TC1C_CODE_EXECUTION`. Запрещённые слова
  сервера — фильтр, а не песочница.
- Учётки не хранить в скилле: `user`/`password` приходят от владельца или из `.env`
  сервера вне git. Пароль `launch_client` виден в списке процессов ОС.
- Закрывай запущенные клиенты по окончании работы.

## Если инструментов `tc_*` нет

Сервер можно погонять пробником без MCP-клиента:

```bash
cd D:/Project/MCP/1c-testpilot
uv run --with mcp python tools/tp.py steps.json     # [{"tool": "...", "args": {...}}]
echo '[{"schema":"tc_field"}]' | uv run --with mcp python tools/tp.py -   # описание инструмента
```

Снимки экрана пробник кладёт в `tools/shots/`.

Пробник сам журналов не ведёт, а логирование обязательно: первым шагом
steps-файла ставь `{"tool": "tc_session", "args": {"action": "start_logging"}}`,
последним — `stop_logging`. Иначе прогон не оставит журнала в `logs/session-*/`
сервера — так прогоны 1118 остались только steps-файлами.

## Подтверждённые грабли и восстановление

Эти случаи подтверждены испытаниями 1103/1109 и прогонами заявок 1102 и 1114:

- `launch_client` с `ok: true` не означает, что база открыта. Если пользователь или
  пароль не переданы, клиент может зависнуть на невидимом для протокола окне
  «Доступ к информационной базе». Сразу проверяй `get_active_window`, а при
  `addressable: false` — `get_screenshot`; перезапускай с точными `user`/`password`.
- При двух и более клиентах передавай `connection_id` во **все** последующие вызовы.
  После обрыва TCP подключайся заново через `tc_session(action="connect", port=...)`
  и заново получай refs: старые ссылки могут стать недействительными.
- Подключения принадлежат процессу сервера TestPilot, а не MCP-сессии. После работы
  делай `stop_client` для каждого своего подключения и подтверждай
  `list_connections: []`; чужие клиентские сеансы не останавливай.
- Панель разделов, «Все функции» и «Файл → Открыть» обычно не адресуются. Навигацию
  делай через известные `e1cib/list/...` и `e1cib/app/...`. Внешнюю обработку нельзя
  считать открытой, пока форма не найдена и не прочитана.
- Для внешней обработки MCP Toolkit рабочий вариант — расширение-пускач с адресуемой
  обработкой, например:
  `e1cib/app/Обработка.ТКТ_ЗапускТулкита`. В форме пускача явно задай свободный порт
  и режим встроенного сервера. Для тестовых сеансов используй отдельные порты (1102:
  ЗУП — 6103, БП — 6104), не порты владельца (6003/6004).
- Toolkit, открытый через временное хранилище пускача, не поддерживает
  `restart_1c_session`: тулкит видит `e1cib\\tempstorage\\...` вместо пути к EPF.
  Перезапускай клиент целиком (`stop_client` → `launch_client`) и снова открывай
  пускач; расширение при этом не пересобирай, достаточно заменить актуальный EPF.
- `click` по скрытому пункту меню может вернуть принятое действие, но не вызвать
  обработчик. Признаки реального успеха — новое окно, сообщение, изменение формы или
  запись в журнале. Если их нет, сними скриншот, проверь переполнение командной панели,
  переоткрой форму и повтори через видимый адресуемый элемент; координатные клики не
  используй.
- Платформенные окна («Установка соединения с 1С:Документооборот», вопросы сохранения)
  закрывай как обычные формы и после каждого закрытия заново читай активное окно.
- Отчёты и большие списки догружаются после команды. `rows: 0` сразу после
  «Сформировать» — не доказательство пустого результата: подожди появления таблицы и
  повтори `read_document`.
- `find_rows` работает только на активной форме и ищет подстроку; ошибка
  `target_not_interactive` означает неверную активную форму, а не отсутствие данных.
  При ошибке колонки используй возвращённый `available_columns`.
- Клик по кнопке в форме документа может закрыть клиент 1С: следующие вызовы
  отвечают «The test-client connection is closed», а повторный `connect` на
  прежний порт отказывает (`WinError 10061`). Восстановление — только
  `launch_client` заново; доказательство после рискованного клика добирай
  `tc_execute_query`, а не чтением окна (дважды в ночных прогонах 1114).
- `stale_ref` после переоткрытия формы — штатный отказ, а не поломка: refs
  протухли, перечитай их `find_objects` и продолжай.

## Практические навыки инженера

- Перед сценарием делай короткий preflight: жив ли сервер 6014, какие подключения уже
  существуют, какая база/версия/учётка выбраны, какие порты заняты. Не поднимай второй
  клиент на месте сеанса владельца.
- Для проверки прав используй цикл: воспроизвести симптом под тестовым пользователем →
  прочитать журнал регистрации через Toolkit → добавить минимально необходимое право →
  повторить сценарий → выполнить регрессию. Не угадывай права по одному экрану.
- Разделяй обязанности: TestPilot управляет UI, Toolkit читает журнал/метаданные и
  подтверждает серверный результат. Для каждой команды сохраняй доказательство
  (скриншот, прочитанное поле/строку, сообщение или запись журнала).
- Для метаданных и быстрых проверок запросом сначала пробуй штатную обработку
  (`tc_get_metadata`, `tc_execute_query`) — пускач и тулкит нужны для журнала
  регистрации и сложных серверных сценариев.
- Открывай только нужные элементы: `find_objects` → точный `ref` → действие →
  read-back. Большой `get_context` оставляй для первичного обзора формы.
- Логирование обязательно на любом прогоне, не только сложном: `start_logging` до
  первого действия, `stop_logging` после последней проверки; для пробника — первый
  и последний шаг steps-файла.
- Отказ одного вызова — не отказ кейса: читай `code` и иди в обход. Ожидаемый
  отказ формы — успешный результат негативной проверки: в приёмке 1114 «сумма
  больше» и «отрицательная» отвергнуты формой, и это цель кейса, а не сбой.
- В рабочих базах выполняй только чтение. Любая запись, проведение, удаление или
  изменение настроек требует явного разрешения; для записи используй демо/тестовую
  копию и всё равно подтверждай результат чтением.

## Рабочие паттерны

### TestPilot → пускач → Toolkit

Когда нужно одновременно пройти интерфейс и объяснить серверную причину ошибки:

```text
list_connections
  → launch_client(test base, explicit user/password)
  → close startup dialogs
  → execute_command(e1cib/app/Обработка.ТКТ_ЗапускТулкита)
  → set explicit test port / start embedded server
  → TestPilot: reproduce UI symptom
  → Toolkit: read event log / query metadata
  → TestPilot: retest and capture evidence
  → stop_client → list_connections
```

### Известный метаобъект → стабильный ref → проверка результата

Не ищи разделы кликами. Открой форму по `e1cib/...`, дождись `Table`, найди элементы
по имени, выполни одно действие и немедленно прочитай результат. `ok: true` трактуй как
«команда принята», а не как «бизнес-операция завершена».

### Безопасная итерация прав

```text
симптом → точный журнал отказа → одно минимальное право → повторный прогон
       → регресс ранее успешных сценариев → фиксированный changelog
```

Такой паттерн применён в заявке 1102: TestPilot поднимает тест-клиент `Zup_1`, Toolkit
работает на отдельном 6103, сеанс владельца 6003 не затрагивается.

### Сквозной обмен между двумя базами 1С: ЗУП → БП

Для обмена держи два независимых тестовых клиента: один для ЗУП, второй для БП. Сразу
после `list_connections` зафиксируй для каждого `connection_id`, базу, пользователя,
порт и версию. Во всех последующих вызовах передавай правильный `connection_id`; не
ориентируйся только на одинаковый заголовок окна или на последний активный клиент.

Порядок, который даёт воспроизводимый результат:

```text
preflight двух клиентов и свободных портов
  → start_logging для прогона
  → проверить и записать read-back настроек транспорта в обеих базах
  → загрузить комплекты правил в оба узла (архив ровно из трёх XML-файлов)
  → проверить правила регистрации и исходные данные для сценария
  → создать документ в ЗУП с несколькими сопоставленными подразделениями и одним без соответствия
  → дождаться завершения обмена
  → прочитать документ и все нужные колонки в БП
  → отдельно проверить проведение и движения
  → сохранить сообщения/стек и сделать регресс
```

Грабли обмена и приёмки:

- Настройка транспорта — не доказательство обмена. После записи пути перечитай значение
  из формы/хранилища и проверь существование каталога вне 1С. В прогоне 1117 отображались
  разные пути `D:\Project\ArtifactsI7\exchange` и `D:\Project\Artifacts\1117\exchange`;
  подобное расхождение нельзя объяснять на глаз — итогом считается только фактический
  read-back и успешный обмен.
- Успешная загрузка документа в БП доказывает только обменную часть. Заполненная форма,
  отсутствие транспортной ошибки или `ok: true` не доказывают проведение. Принимай
  отдельно: документ дошёл, строки/реквизиты заполнились, документ проведён, движения
  сформированы. Для каждого результата нужен read-back из объекта/списка/регистра.
- Проверяй не только шапку: в новом документе прочитай табличную часть, подразделения,
  «Способ отражения» и сценарий без соответствия. Пустое подразделение без соответствия
  может быть согласованным результатом, а предупреждение «Возможно ошибочно не
  заполнена...» — диагностическим сообщением, не транспортной ошибкой; сохрани его
  текст и отдельно оцени бизнес-критерий.
- Долгая синхронизация и проведение выполняются асинхронно. После запуска жди завершения
  задания, перечитай активную форму/сообщения и только потом делай вывод. Если форма
  переоткрыта, старые `ref` перечитай заново.
- Расширение нельзя выключать целиком, чтобы получить зелёный результат. Для
  дифференциальной диагностики допустимо временно сравнить «включено/выключено», но это
  только локализация: если при включённом расширении проведение **не работает**, а при
  отключённом **работает**, фиксируй `обмен PASS; проведение FAIL/BLOCKED; причина —
  стек/код`, восстанови расширение включённым и ищи точечную изоляцию старого кода.
  Такой результат не закрывает задачу и не оправдывает отключение доработок других задач.
- При ошибке «Поле объекта не обнаружено» фиксируй полный объект, модуль, процедуру и
  строку стека. В 1117 обращение `Реквизиты.Регистратор.К_ВидРезерва` в
  `ГПИ_Доработки ОбщийМодуль.УчетЗарплаты.Модуль(4557)` падало только при включённом
  расширении; это указатель на конфликт старого перехвата с новым типовым документом,
  а не повод считать типовой механизм исправленным после отключения расширения.
- После временной смены транспорта, загрузки правил или состояния расширения обязательно
  сделай read-back конечного состояния и верни тестовую среду в согласованное состояние.
  В журнале отдельно запиши, что было временно изменено, что восстановлено и что осталось
  блокером.

Для итоговой записи используй раздельные формулировки: «обмен выполнен и проверен»;
«проведение при включённых доработках не работает»; «при отключении работает — это
диагностический результат»; «расширение восстановлено включённым». Не заменяй их общей
фразой «типовой механизм проверен».
